# allocwatch

Помощник плагина: слушает работающий процесс .NET и раз в секунду сообщает, **какая строка исходника сколько выделяет памяти**.
Плагин пишет эти числа в редакторе — в конце строки, у объявления метода и полосой слева. Измерения и цена подхода — в
`tools/alloc-probe/README.md` (зонд, с которого всё началось).

| Что | Где |
|---|---|
| исходник | `allocwatch/Program.cs`, проект `allocwatch/AllocWatch.csproj` |
| сборка на машине пользователя | `cli/DotNetHelper` (общий с индексатором сборок) |
| служба, отрисовка, переключатель | `allocations/AllocationsService.kt` |
| разбор сообщений и тексты | `allocations/AllocationModel.kt` |
| фикстура и тест | `src/test/resources/allocations/watcher.jsonl` (настоящий вывод помощника), `AllocationsTest` |
| проверка вживую | `debug-playground/Console/Allocations.cs`, профиль `Allocations` |

## Запуск

```sh
dotnet build allocwatch -c Release
dotnet allocwatch/bin/Release/net8.0/AllocWatch.dll --pid <pid>[,<pid>...] --root <папка исходников> [--window 10] [--interval 1] [--wait 20]
```

- `--pid` — кандидаты, вероятнейший первым: `dotnet run` — это запускающий процесс, программа — его потомок. Берётся первый, у кого
  есть диагностический порт; пока его нет (программа ещё стартует), помощник ждёт до `--wait` секунд.
- `--root` — аллокация записывается на первый кадр стека, чей исходник лежит под этой папкой.
- `--window` — за сколько последних секунд считаются числа строки.
- Остановка — закрыть помощнику стандартный ввод: он отпускает сессию, программа работает дальше. Сам он завершается, когда
  завершается программа.

## Сообщения

По строке JSON в стандартный вывод:

```
{"started":true,"pid":49256}
{"seconds":3,"window":3,"bytesPerSecond":20664748,"events":586,"lines":[
  {"file":"C:\\…\\Allocations.cs","line":65,"method":"Playground.AllocationScenario.Buffer()",
   "bytesPerSecond":19430864,"objectsPerSecond":18541,"share":95,"totalBytes":58744408,"types":{"System.Byte[]":100}}, …]}
{"stopped":true,"reason":"stopped"}
```

`bytesPerSecond`, `objectsPerSecond`, `share`, `types` — за окно; `totalBytes` — за всё время; `share` — доля от записанного на строки
исходников. Строк не больше 400, по убыванию байтов.

## Как это устроено

- EventPipe (`Microsoft.Diagnostics.NETCore.Client`), провайдер `Microsoft-Windows-DotNETRuntime`, уровень Verbose, ключевые слова
  GC, JIT, Loader, JittedMethodILToNativeMap.
- Разбор на лету — `TraceLog.CreateFromEventPipeSession` (`Microsoft.Diagnostics.Tracing.TraceEvent`): стеки доступны сразу, файл
  трассы не пишется. Сведения о методах, скомпилированных до подключения, даёт rundown при старте сессии.
- Событие `GCAllocationTick` — выборка: примерно раз на 100 КБ, выделенные потоком.
- Строка — по portable PDB рядом со сборкой; адрес, у которого нет строки (скрытый код компилятора), пропускается, берётся кадр выше.

## Сборка у пользователя

Как у индексатора: плагин несёт `Program.cs` и `.csproj`, собирает под SDK машины (`-p:HelperFramework=net10.0`). Проверено
2026-09-29 на SDK 10.0.401 и 9.0.301: 1,5 и 2,3 с при пакетах в кэше NuGet; результат — 14–15 МБ в кэше IDE.

**Отличие от индексатора**: нужны два пакета NuGet. Если их нет в кэше машины, первая сборка идёт в сеть за пакетами; без сети
и без пакетов помощник не соберётся — плагин покажет уведомление с причиной, остальное работает.

## В редакторе

- Переключатель — меню .NET → Show Allocations in Editor (по проекту, запоминается, **по умолчанию выключен**). Где он: меню **.NET** в главной строке меню, пункт сразу под «Monitor .NET Process»; ПКМ в редакторе файла `.cs`, последний пункт; Ctrl+Shift+A → «Show Allocations in Editor». Это пункт меню с галочкой, в Settings его нет.
  Включён — плагин
  подключается к программе, запущенной конфигурацией «.NET Project» (Run и Debug), к самой новой из запущенных.
- Тому, кто включил переключатель, плагин отвечает уведомлением: программа не запущена / слушаю такую-то. Программы, запущенные
  позже, подключаются молча. Неудача (помощник не собрался, программа не найдена среди процессов запуска, помощник не смог
  подключиться) — всегда уведомление об ошибке с причиной; весь путь пишется в `idea.log` со словом `Allocations`.
- Программа среди процессов запуска (`dotnet run` → программа, рядом `conhost.exe`, узлы MSBuild) ищется по командной строке.
  Java на Windows её не сообщает (`ProcessHandle.Info.commandLine()` пуст, есть только путь к исполняемому файлу) — берётся список
  процессов платформы (`OSProcessUtil.getProcessList()`, около 0,35 с), один раз на каждый новый процесс дерева. Процесс, о котором
  известно только `dotnet.exe` без аргументов, программой не считается.
- В конце строки: `19.3 MB/s, 18.4K obj/s, byte[]  95%`; строка с долей от 25% — цветом полосы, остальные — серым.
- У объявления метода, в котором выделяют несколько строк: `allocates 98 KB/s  0.5%`.
- Полоса слева тем плотнее, чем больше доля; подсказка полосы — типы с долями, всего с момента подключения, метод.
- Числа привязаны к строкам **сборки**. После подключения правки в файле их не сбивают (за строками следят маркеры документа); если
  файл правили между сборкой и запуском, числа с самого начала стоят не на тех строках — пересобрать и запустить заново.
- Программа завершилась или переключатель выключен — числа убираются.

## Ограничения

- Выборка: строка, выделяющая мало, появляется и пропадает; за окно в 10 с мелкое может не попасть вовсе.
- Скрытый код (объект замыкания, встроенные методы в Release) уводит аллокацию на вызывающую строку.
- Пакеты без PDB: их аллокации записываются на строку кода пользователя, которая их вызвала, — это и нужно.
- Цена — около 2,4 мкс на событие: не измерима при десятках МБ/с, 28% при 12 ГБ/с.
- Проверено на .NET 9, сборка Debug. Событие `AllocationSampled` из .NET 10 не запрашивается.
- Один процесс за раз.
