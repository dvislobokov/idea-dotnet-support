# alloc-probe

Зонд, к сборке плагина не относится. Вопрос, на который он отвечает: **можно ли по работающему процессу узнать, какая строка
исходника сколько выделяет памяти** — чтобы показывать это в редакторе. Ответ (2026-09-29): да, привязка к строкам точная.

```sh
dotnet build tools/alloc-probe -c Release
dotnet tools/alloc-probe/bin/Release/net8.0/AllocProbe.dll --pid <pid> [--seconds 10] [--root <папка исходников>] [--out <файл.json>] [--keep <файл.nettrace>]
```

Цель для проверки — `debug-playground/Console`, сценарии `allocations` (десять кругов в секунду, с паузой) и `allocations-fast`
(без паузы, печатает число кругов в секунду); строки, которые выделяют память, помечены `// ALLOC:<имя>` с ожидаемой долей.

## Как устроено

- Подключение к процессу — `Microsoft.Diagnostics.NETCore.Client` (EventPipe, тот же канал, что у `dotnet-counters` и `dotnet-trace`).
  Процесс перезапускать и собирать особым образом не нужно.
- Провайдер `Microsoft-Windows-DotNETRuntime`, уровень Verbose, ключевые слова GC, JIT, Loader и JittedMethodILToNativeMap
  (последнее — чтобы адрес кода перевести в смещение IL, а его — в строку).
- Событие `GCAllocationTick`: среда поднимает его примерно на каждые 100 КБ, выделенные потоком, с типом объекта, перешедшего
  отметку, его размером и стеком. Это **выборка**, а не учёт каждого объекта.
- Разбор — `Microsoft.Diagnostics.Tracing.TraceEvent`: `TraceLog` по файлу `.nettrace`, строка исходника — `GetSourceLine` по
  portable PDB рядом со сборкой.
- Аллокация записывается на **первый кадр стека, чей исходник лежит под `--root`**, считая от места выделения наружу: на строку
  кода пользователя, даже если память выделил код фреймворка, вызванный с этой строки (`numbers.Add(i)` → массив внутри `List`).
- Число объектов — оценка: байты между событиями, делённые на размер объекта из события.

## Что получилось

Сценарий `allocations`, 10 секунд, .NET 9, сборка Debug:

| Строка | Что на ней | Ожидалось | Измерено | Событий |
|---|---|---|---|---|
| `return new byte[1024];` | `ALLOC:buffers` | ≈ 95% байтов | 95,1%, 19,3 МБ/с, 18 401 объект/с | 1 810 |
| `return $"order-{round}-{index}";` | `ALLOC:strings` | ≈ 4%, объектов столько же | 4,5%, 0,9 МБ/с, 18 802 объекта/с | 85 |
| `numbers.Add(i);` | массивы `List` при росте | ≈ 0,4% | 0,3%, тип `Int32[]` | 5 |
| `return value;` | `ALLOC:boxing` | ≈ 0,2% | 0,2%, тип `Int32` | 3 |
| `new List<int>()`, замыкание | десятки байт на круг | — | **не попали в выборку** | 0 |

Сверка: буферов и строк создаётся поровну — измерено 18 401 и 18 802 в секунду; строка `"order-12-345"` занимает 48 байт — измерено
48 байт на объект. Из 1 910 событий 1 903 записаны на строки площадки, остальные 7 — служебные аллокации самой трассировки.

Сценарий `allocations-fast` (12 ГБ/с, 1,16 млн событий за 10 с) — видно и мелкое: делегат (33 события), объект замыкания (11),
сам `List` (6).

## Цена

| | `allocations` (20 МБ/с) | `allocations-fast` (12 ГБ/с) |
|---|---|---|
| событий в секунду | 191 | 115 600 |
| замедление программы | не измеримо | 28% (7 684 → 5 535 кругов/с), после отключения — 7 597 |
| файл трассы за 10 с | 0,46 МБ | 105 МБ |
| разбор трассы | 0,26 с | 2,6 с |

Цена пропорциональна частоте событий, то есть скорости аллокаций: около 2,4 мкс на событие. Обычное приложение (десятки МБ/с)
её не заметит; программа, которая только и делает, что выделяет гигабайты в секунду, замедляется на четверть.

## Ограничения

- **Выборка.** Строка, выделяющая мало, за десять секунд может не получить ни одного события: её нет в отчёте, хотя память она
  выделяет. Чем дольше слушать, тем мельче видно.
- **Место записи неточно для скрытого кода.** Объект замыкания создаётся до первой строки метода, у этой инструкции нет строки
  исходника — аллокация уходит кадром выше, на строку вызова (`Sink[1] = Counter(round)`, а не внутрь `Counter`). То же будет со
  встроенными (inlined) методами в Release.
- **Debug и Release различаются.** В Release часть аллокаций исчезает (встраивание, размещение на стеке в .NET 10), строки
  сдвигаются. Измерять надо ту сборку, которую запускает пользователь.
- Нужны PDB рядом со сборками (у проектов solution они есть, у пакетов — обычно нет: их аллокации записываются на вызывающую строку).
- Проверено на .NET 9. В .NET 10 есть событие `AllocationSampled` со случайной выборкой (ключевое слово `0x80000000000`) —
  статистически точнее для мелких объектов; зонд его не запрашивает.
- Зонду нужны два пакета NuGet (на этой машине они были в кэше): в отличие от индексатора сборок, помощник плагина не соберётся
  на машине пользователя без сети при первом запуске.
