# indexer

Индексатор сборок .NET: читает метаданные `.dll` (пакеты NuGet, эталонные сборки SDK, собранные проекты solution) и пишет индекс
того, что из сборки видит чужой код: публичные и protected типы целиком (generic-параметры с ограничениями, база, интерфейсы,
атрибуты) и все их публичные и protected члены с сигнатурами — по файлу на сборку, плюс файл документации из `<сборка>.xml`.
Плагин по нему предлагает то, что не импортировано (`WriteLi` → `Console.WriteLine(|);` и `using`), без запроса к серверу и до
загрузки solution; с формата 2 (0.1.52) это ещё и источник типов библиотек для своей семантики (шаг 11 `CSHARP_PSI_MIGRATION.md`).

| Что | Где |
|---|---|
| исходник | `indexer/Program.cs`, проект `indexer/AssemblyIndexer.csproj` |
| сборка и запуск на машине пользователя | `src/main/kotlin/io/github/dotnetsupport/index/IndexerTool.kt` |
| список сборок проекта | `index/ProjectAssemblies.kt` (по `obj/project.assets.json`) |
| читатель индекса | `index/AssemblyIndex.kt` (типы, члены), `index/IndexedTypeRef.kt` (ссылки на типы), `index/AssemblyDocs.kt` (документация) |
| вопросы резолвера по всем сборкам проекта | `index/AssemblyIndexSet.kt` |
| элементы completion и автоимпорт | `index/ImportCompletion.kt`, `lang/CSharpCalls.kt` (`CSharpUsings`) |
| фикстуры и тесты | `src/test/resources/index/*.dnix`, `*.dnxd`, `AssemblyIndexTest`, `AssemblyIndexSemanticsTest`, `ImportCompletionTest`; сборка-фикстура — `tools/index-fixture` |
| проверка вживую | `debug-playground/Console/Editor/ImportCompletion.cs` |

## Сборка на машине пользователя

Собранного dll в репозитории и в плагине **нет**: плагин несёт `Program.cs` и `AssemblyIndexer.csproj` (их кладёт в ресурсы
`processResources`) и собирает их сам при первом обращении:

1. `dotnet --version` в папке кэша — какой SDK будет собирать (самый новый из установленных);
2. целевая платформа — по нему: SDK 10 → `net10.0`, SDK 9 → `net9.0`, SDK 8 → `net8.0`. Эталонный пакет **своей** версии у SDK всегда
   с собой, поэтому сборке не нужна сеть; собирать под `net8.0` на машине с SDK 9 / 10 значило бы качать эталонный пакет .NET 8;
3. `dotnet build AssemblyIndexer.csproj -c Release -o <кэш>/bin -p:IndexerFramework=net10.0`;
4. результат — `<system IDE>/dotnet-support/indexer/<хэш исходника>-<платформа>/bin/AssemblyIndexer.dll`. Другой исходник (новая
   версия плагина) или другой SDK — другая папка, старая не мешает.

Проверено 2026-09-29 на SDK 10.0.401 и 9.0.301: сборка 2,2 и 2,5 с, индексы обеих сборок побайтно одинаковы. SDK старше 8 или его
отсутствие — индекс выключен, причина в `idea.log` («The indexer needs the SDK…»), остальной плагин работает. Неудача сборки
запоминается до перезапуска IDE, чтобы не собирать на каждое completion.

Руками (для фикстур и замеров):

```sh
dotnet build indexer -c Release                      # net8.0, если не задан IndexerFramework
dotnet indexer/bin/Release/net8.0/AssemblyIndexer.dll --out <папка> [--list <файл с путями>] [--force] [--wait <секунд>] [<сборка>...]
dotnet indexer/bin/Release/net8.0/AssemblyIndexer.dll --version      # версия формата
```

На стандартный вывод — строка JSON на сборку (`path`, `mvid`, `index`, `types`, `members`, `bytes`, `docs`, `docBytes`, `ms`, либо
`skipped`, либо `error`),
последней строкой — сводка (`summary`, в ней `waited` — сколько ждали блокировку). Сборка без метаданных (нативная dll) — `error`,
остальные обрабатываются дальше.

Сборки индексируются параллельно, на половине ядер (IDE тоже работает); строки JSON — в порядке списка.

Фикстуры тестов — индексы и документация `System.Console.dll`, `System.Linq.dll`, `System.Collections.dll` (и индекс без документации `System.Runtime.dll` — для типов выражений) из `Microsoft.NETCore.App.Ref`
10.0 и сборки `tools/index-fixture` (записи, `init` / `required`, nullable, кортежи, ограничения, наследование generic-типов, protected,
значения по умолчанию, операторы, события, индексаторы, extension-методы всех видов) и `tools/index-fixture/access` (`AccessFixture.dnix`, для
ошибок доступа: internal и private типы, internal и private protected члены, аксессоры уже свойства, `InternalsVisibleTo` с ключом и без).
Пересоздать все разом (из корня, Git Bash):

```sh
sh tools/index-fixture/fixtures.sh       # собирает индексатор и сборку-фикстуру, кладёт <имя>.dnix / .dnxd в src/test/resources/index
```

## Несколько IDE и несколько проектов

Один и тот же индекс не строится дважды:

- **между процессами** — индексатор на время работы держит открытым `<папка индексов>/.lock` без разделения доступа. Второй индексатор
  ждёт (по умолчанию до 120 с, `--wait`), потом видит готовые файлы и пропускает их. Блокировку снимает система, когда процесс
  завершается, как бы он ни завершился, — «зависшей» блокировки не остаётся. Проверено: три индексатора разом на одну папку — один
  проиндексировал 167 сборок за 0,43 с, два ждали 0,44 и 0,57 с и пропустили все 167;
- **сборка самого индексатора** — под блокировкой `<кэш>/indexer/.lock` (`FileChannel.lock`): вторая IDE ждёт первую и находит готовый dll;
- **внутри одной IDE** — проекты (окна) запускают индексатор по очереди (`IndexerTool.index` синхронизирован), а все проекты одного
  solution идут одним запуском;
- запись индекса — во временный файл и переименованием: читатель никогда не видит недописанный файл.

## Размер кэша

Кэш общий на машину (`<system IDE>/dotnet-support/index/v<формат>`), растёт только на те сборки, которые нужны открытым проектам.
Таблица ниже — замер формата 1 (только статические члены); формат 2 в 2,5–4 раза больше плюс документация, см. «Замеры».

| Что | Сборок | Данные | На диске | Индексация |
|---|---|---|---|---|
| `debug-playground`, проект `Console` | 164 | 1,5 МБ | 1,9 МБ | 0,48 с |
| проект `Web` (ASP.NET) | 302 | 1,9 МБ | 2,6 МБ | 0,78 с |
| проект `Tests` (xunit) | 179 | 1,6 МБ | 2,0 МБ | 0,50 с |
| весь solution (5 проектов) | 317 разных | 2,0 МБ | 2,8 МБ | 0,73 с |
| для сравнения: вся `~/.nuget/packages` | 12 292 | 83 МБ | 103 МБ | 25 с |

Проекты одного solution делят почти все сборки: пять проектов — это не пять раз по 2 МБ, а 2 МБ. В памяти JVM индекс не лежит:
файлы отображены в память (страницы общие для всех проектов и всех IDE), в куче — только ссылки на уже запрошенные строки.
Устаревшие индексы (пакет обновили, старая версия больше не нужна) не удаляются: они малы, а старая версия может понадобиться
другому проекту. Очистка — удалить папку кэша, индексы построятся заново.

## Что попадает в индекс

- все типы (с версии 4): публичные и вложенные protected / protected internal (пометка `isProtected`) — те, что видит чужой код; internal
  (пометка `isInternal`) и private (`isPrivate`, без членов) — после них, чтобы чужой код получал CS0122, а не «нет такого типа», а
  сборка-друг их видела. Вид: class, struct, interface, enum, delegate, static class; пометки abstract, sealed, static, record
  (record class — по методу `<Clone>$`; record struct в эталонной сборке следов не оставляет), readonly struct, ref struct;
- у типа — все generic-параметры (у вложенного — и внешних, как в метаданных) с вариантностью и ограничениями (`class`, `struct`,
  `new()`, `unmanaged`, `allows ref struct`, типы), база (у класса), интерфейсы (метаданные перечисляют и унаследованные), вложенные
  типы, атрибуты (полные имена, без служебных атрибутов компилятора), базовый тип enum;
- все члены, кроме private, экземплярные и статические: методы, extension-методы, конструкторы (не статические), операторы
  и преобразования, свойства и индексаторы (видимые аксессоры, `init`, `required`; доступность геттера и сеттера — кодом во флагах),
  события, поля (`readonly`), константы и значения enum со значением (`"text"`, `42`, `1.5F`). Internal и private protected (с версии 4)
  — после тех, что видят все: компилятор импортирует internal только для сборки-друга, а private protected — всем (и говорит CS0122);
- `[assembly: InternalsVisibleTo]` сборки: имя друга, `Имя,key`, если в атрибуте есть открытый ключ (тогда друг — только подписанная им
  сборка; неподписанный проект с тем же именем другом не считается);
- у методов — тип результата и параметры с именами, `ref` / `out` / `in` / `params` / `this`, значением по умолчанию; generic-параметры
  метода; пометки static, abstract, virtual, override, sealed, readonly;
- типы в сигнатурах — ссылками (ниже), с аннотациями nullable reference types из `[Nullable]` / `[NullableContext]` и именами
  элементов кортежей из `[TupleElementNames]`; `dynamic` (`[Dynamic]`) пока виден как `object`, расширения C# 14 (`extension(T)`) —
  только через их методы-реализации;
- пометки `[Obsolete]` и `[EditorBrowsable(Never)]` (такое в индексе есть: код, который его называет, прав, — но completion его не
  предлагает);
- документация из `<сборка>.xml` рядом с dll (эталонные пакеты SDK и пакеты NuGet её несут) — отдельным файлом `<mvid>.dnxd`.

Сборка не загружается и не исполняется: читаются только таблицы метаданных.

## Что спрашивает плагин

`AssemblyIndex` — одна сборка: `types(prefix)` / `members(prefix)` (типы и статические члены по началу имени — для completion без
импорта; protected там нет), `findType("System.Collections.Generic.Dictionary`2+Enumerator")` и `typesIn(namespace)` — двоичным
поиском, `type.members` / `baseType` / `interfaces` / `typeParameters` / `nestedTypes` / `attributes`, `extensions(ключ)` — extension-методы
по тому, что они расширяют (метаданное имя типа без аргументов, `[]` — массив, `!` — параметр типа метода), `doc(docId)`.
`AssemblyIndexSet` — все сборки проекта (`AssemblyIndexService.symbols(projectFile)`): тип по имени в любой из них, цепочка баз и все
интерфейсы с подстановкой аргументов (`class MyList : List<int>` → `IList<int>`), члены с унаследованными (переопределённое и скрытое —
один раз), extension-методы для типа получателя, документация. ID документации членов (`IndexedMember.docId`) — как у компилятора;
проверено на всех членах `System.Console`, `System.Linq`, `System.Collections` (тест).

## Ключ и хранение

Файл называется по MVID модуля: `<mvid>.dnix`. Пакет NuGet данной версии и эталонная сборка SDK не меняются, значит и их индекс
строится один раз и не требует сброса. Проект — это список сборок, а не свой индекс. Одна и та же сборка в разных пакетах и под
разные TFM даёт один файл. Собранный проект solution после пересборки получает новый MVID — и новый индекс.

## Что видит проект

Только то, с чем он компилируется (`ProjectAssemblies.references` → `References`: `assemblies`, `projects`, `projectOutputs`; у
сервиса — `AssemblyIndexService.references(projectFile)` и `symbols(projectFile)`):

- сборки `compile` его пакетов из `project.assets.json` — транзитивные в том числе; зависимости, которые автор пакета пометил
  приватными, в `compile` не попадают и не предлагаются;
- эталонные пакеты фреймворков, на которые он ссылается (`frameworkReferences`): `packs/<имя>.Ref/<версия>/ref/<tfm>/`, самый новый
  патч; пакета нет в SDK (`net8.0` у SDK 10) — тот, что restore скачал в папку пакетов (`downloadDependencies`);
- .NET Framework (`net472`, `net48`): эталонные сборки из пакета `Microsoft.NETFramework.ReferenceAssemblies.net4x`
  (`build/.NETFramework/v4.x/`), без него — из `Reference Assemblies\Microsoft\Framework\.NETFramework\v4.x` машины (и `Facades`):
  `mscorlib`, что SDK добавляет сам (`System`, `System.Core`, `System.Xml`…), и названное в `<Reference Include>`;
- `<Reference><HintPath>` — файл по пути от проекта;
- проекты, от которых он зависит, — **проектами** (`projects`: это исходники, их видит своя семантика); их собранная эталонная
  сборка из `obj/<конфигурация>/<tfm>/ref/` (или из `bin`, у старого формата — `bin/<конфигурация>/`) — отдельно (`projectOutputs`),
  её индексирует индексатор, пока completion без импорта смотрит только на метаданные;
- проект старого формата (без `project.assets.json`): `TargetFrameworkVersion`, `Reference` (с `HintPath` — пакеты `packages.config`),
  `ProjectReference` из самого файла проекта.

Целевая платформа — выбранная в тулбаре, если она у проекта есть, иначе первая. Пересчёт — после restore (`project.assets.json`),
правки файла проекта, смены платформы в тулбаре (`CompilationModel.CHANGED`), Reload. Пакеты, которых нет в проекте, не предлагаются.

## Формат (версия 4)

Все числа — `int32`, little-endian. Меняется формат — поднять `Program.FormatVersion` и `AssemblyIndex.FORMAT_VERSION` и пересоздать
фикстуры. Список — индекс в таблице int: число элементов, затем элементы (0 — пустой список, одинаковые списки хранятся один раз);
-1 — нет строки / ссылки / типа.

```

           для строк, типов, членов, параметров, generic-параметров, int, имён, extension: число записей и смещение
           (у типов и членов — число тех, что видит чужой код), всего типов, всего членов, друзья (список строк
           InternalsVisibleTo)                                                                                            108 байт
строки     (число + 1) смещений в данные, которые идут следом, UTF-8

           сначала члены, которые видят все, потом только для друга (internal, private protected; все члены internal-типов).

           у свойства и индексатора доступность геттера — `(флаги >> 15) & 7`, сеттера — `(флаги >> 18) & 7`: 0 нет (или
           private), 1 public, 2 protected, 3 internal, 4 protected internal, 5 private protected. Флаги типа: 512 internal, 1024 private

           что видит чужой код (internal для друга плагин находит по членам типа)
```

Ссылка на тип — строка (их общий пул делит одинаковые) маленькой префиксной грамматики, плагин разбирает её по требованию
(`IndexedTypeRef.parse`): `NSystem.String;` / `VSystem.Int32;` — ссылочный / значимый тип по метаданному имени, `I2:<определение><аргументы>`
— generic-экземпляр (у кортежа — `I2{Count,}:…` с именами элементов), `!0;` / `M0;` — параметр типа / метода, `[` — массив, `A2;` —
многомерный, `*` — указатель, `&` — `ref` результата, `F<n>:` — указатель на функцию, `?` впереди — аннотированный nullable reference.
Полное описание — `TypeRefs` в `Program.cs`.

Nullability члена (версия 3, для анализа потока nullable — `lang/semantic/CSharpNullableFlow`, читает `index/IndexedNullability`) — строка
пунктов `цель:код` через `;`, -1 — ничего. Цель: `r` — возвращаемое значение метода, тип свойства или поля; `0`, `1`… — параметр; `m` — сам
член. Коды: `o` — oblivious (ссылочный тип без nullable-контекста: старый код, где `string` может быть null), `M` / `N` / `A` / `D` —
`[MaybeNull]` / `[NotNull]` / `[AllowNull]` / `[DisallowNull]`, `W1` / `W0` — `[NotNullWhen(true / false)]`, `w1` / `w0` — `[MaybeNullWhen]`,
`X1` / `X0` — `[DoesNotReturnIf]`, `I=имя` — `[NotNullIfNotNull("имя")]`; у члена: `R` — `[DoesNotReturn]`, `MN=a,b` — `[MemberNotNull]`,
`MW1=a,b` / `MW0=…` — `[MemberNotNullWhen]`. `[MaybeNull]` / `[NotNull]` свойства компилятор кладёт на возвращаемое значение геттера,
`[AllowNull]` / `[DisallowNull]` — на параметр сеттера: индексатор собирает их оттуда в `r`.

Документация `<mvid>.dnxd`: заголовок (`DNXD`, версия, mvid, число записей и блоков), таблица блоков (первый ID, смещение и длина
сжатого блока, длина без сжатия), блоки по ~16 КБ raw deflate; в блоке — записи «ID, байт 1, внутренний XML `member` с пробелами в одну,
байт 0» по порядку ID. Поиск — двоичный по первым ID блоков и просмотр одного блока; плагин держит 8 последних распакованных блоков.
Сжатие записей по одной давало 17 МБ на эталонный пакет, блоками — 3,5 МБ.

Плагин файлы не разбирает: отображает в память и ищет двоичным поиском, строки и ссылки декодируются по требованию.

## Completion

`ImportCompletionContributor` (основная часть плагина, сервер не нужен): по голому имени от трёх букв — статические методы, свойства,
поля и константы типов проекта; перегрузки одной строкой (`Console.WriteLine  ()  +17 overloads  (System)`). Не предлагаются:
после точки, на месте имени объявляемой переменной, в строках и комментариях, extension-методы и значения enum, устаревшее, члены
обобщённых типов, типы, подключённые через `using static`.

Вставка: `Тип.Член`, скобки и точка с запятой по общим правилам (`CSharpCalls`: `void` или вызов, завершающий оператор), `<|>()` у
обобщённого метода без параметров, `using` — в блок директив по порядку (`System` первым, дальше по алфавиту). `using` не добавляется,
если namespace виден и так: директива файла, implicit usings SDK проекта, `global using` (в т.ч. из `obj/**/*.GlobalUsings.g.cs`),
собственный namespace файла.
