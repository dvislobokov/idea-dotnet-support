# C# через roslyn-language-server: план

Статус: **фазы 1–3 и 7 сделаны и проверены в живой IDE 2026-09-21** (что именно проверено и что осталось посмотреть руками — в `ROADMAP.md`), дальше фаза 8 (фазы 4–6 — по замеру загрузки на реальном solution). Чек-лист — в `ROADMAP.md`.

## Задача
Дать плагину семантику C# (ошибки компилятора, completion, переходы, рефакторинги, раскраска) через `roslyn-language-server` и при этом быть
**оптимизированным клиентом**: то, что меняется редко, плагин хранит у себя и отдаёт мгновенно, а не спрашивает сервер каждый раз.
Три слоя, снизу вверх:
1. **Сервер** — платформенный LSP-клиент (`intellij.platform.lsp`) + то, что специфично для Roslyn.
2. **Кэш ответов сервера** — прогрев, персистентные ответы по хэшу содержимого, спекулятивный completion.
3. **Свои данные плагина** — индексы исходников, метаданных сборок и XML-документации: работают без сервера и пока он грузится.

Эвристики плагина (раскраска по токенам, Structure view, folding, отступы, тесты, endpoints) остаются: они работают, когда сервера нет.

## Решения
- **Платформенный LSP-клиент, не свой JSON-RPC.** В 2026.1 модуль есть во всех IDE и без лицензии (проверено в работающей IDE, см.
  `docs/platform-lsp-dap.html`), закрывает 30 из 37 нужных возможностей, включая pull-диагностику, без которой Roslyn бесполезен.
  Прежний план собственного клиента (2026-09-20, писался под GoLand 2025.1.3) снят; он остался в истории git.
- **Сервер — `roslyn-language-server`** (dotnet tool, MIT, .NET 10; проверена версия 5.12). Факты о нём — `tools/roslyn-lsp/README.md`.
- **Уже готово:** страница Settings | Tools | .NET | Language Server, `RoslynLanguageServer.arguments(...)` (командная строка),
  `RoslynLanguageServer.configuration(...)` (ответ на `workspace/configuration`, отступы из Code Style), поиск tool с `.cmd`-шимом на Windows.
- **Что грузит сервер (решение пользователя 2026-09-21).** Есть solution — его всегда называет плагин (`solution/open`), `--autoLoadProjects` при
  этом серверу не передаётся. Solution ищутся по всей открытой папке рекурсивно (мимо `bin` / `obj` / `node_modules` / `packages` и папок с точкой);
  один — открывается молча, несколько — список «Select Solution for C# Language Server», выбор хранится в workspace-файле проекта; закрыли список —
  остаётся нотификация, сменить — меню .NET → Select Solution for Language Server (это перезапуск сервера: он держит один solution). Пока выбор не
  сделан, ничего не загружено и ошибок не показывается. Нет solution — `--autoLoadProjects` (галочка страницы) либо `project/open`.
- **Roslyn главный (решение пользователя 2026-09-21).** Там, где есть и своё, и серверное (folding, отступы при наборе / onTypeFormatting,
  форматирование, раскраска), при работающем сервере отвечает сервер; эвристики плагина — только пока сервера нет или он грузится.
- **LSP4IJ не учитываем** (решение пользователя 2026-09-21): конфликт двойного запуска не проверяем и не предупреждаем.
- **Кто главный:** сервер готов — отвечает он; не готов (нет, грузится, упал) — отвечают индексы и эвристики. Свои данные плагина только
  **предлагают** (completion, переходы, документация, раскраска) и никогда не источник ошибок и правок кода: лишний пункт в списке безобиден,
  ложная ошибка — нет.

## Что показал замер (`tools/roslyn-lsp/bench.py`, сервер 5.12, `debug-playground`, файл 242 строки)

| Запрос | Первый раз | Прогретый (медиана) | Ответ |
|---|---|---|---|
| старт процесса + `initialize` | 0,7 с | — | |
| `solution/open` → `workspace/projectInitializationComplete` (5 проектов) | 3,1 с от старта | — | |
| первая pull-диагностика после открытия | 1,5 с | 1 мс | |
| completion после `person.` | 166 мс | **4 мс** | 9 элементов, `isIncomplete: true` |
| completion на голом имени (`C`, `Co`, … `Console`) | 43 мс | **13 мс** | 665 элементов, 57 КБ, `isIncomplete: false`, **список один и тот же на каждой букве** |
| `completionItem/resolve` | 50 мс | 2 мс | |
| hover | 58 мс | 4,5 мс | |
| signature help | 83 мс | 9,5 мс | 7,7 КБ |
| `semanticTokens/full` / `range` (50 строк) | 146 / 7 мс | 17 / 4 мс | 19 / 6 КБ |
| `documentSymbol`, `foldingRange` | 15–28 мс | 1–2 мс | |

Проверено попутно: `solution/open` — уведомление с `{"solution": "<uri .sln>"}`, конец загрузки — уведомление
`workspace/projectInitializationComplete`. Сервер отдаёт `itemDefaults` (`commitCharacters`, `data`, `editRange`): `data` для resolve
подставляется из defaults.

### Можно ли отвечать быстрее миллисекунды
**Первый ответ в новом контексте — нет, повторный и продолжение набора — да.**
- Нижняя граница живого запроса — 4–13 мс (stdio + Roslyn + разбор JSON), клиентом не лечится. Это меньше кадра (16 мс) и глазом не видно.
- Набор внутри открытого списка: сервер по префиксу не фильтрует, список для `C` и для `Console` одинаков → фильтрация целиком локальная,
  < 1 мс. Платформа это уже делает: `LspCompletionContributor` зовёт `restartCompletionOnAnyPrefixChange` только при `isIncomplete: true`.
- Пользователь реально ждёт в трёх местах, и оптимизация нужна именно там: **холодный старт** (3 с – на большом solution десятки секунд),
  **первые запросы после старта** (40–170 мс), **большие файлы** (время tokens растёт с размером, оценка — ~0,3 с на 5 000 строк).

## Слой 1. Сервер на платформенном клиенте
- **Сделано (фаза 1).** Content-модуль `io.github.dotnetsupport.roslyn` (`resources/io.github.dotnetsupport.roslyn.xml`, зависимость — модуль
  `intellij.platform.lsp.impl`), как с DAP: без LSP плагин обязан работать, остальной код на `com.intellij.platform.lsp.*` и на пакет `roslyn`
  не ссылается. Пакет не `lsp`: в `io.github.dotnetsupport.lsp` лежит страница настроек основной части, а у модуля свой загрузчик по префиксу
  пакета. Мост из основной части — топик `RoslynLanguageServerSettings.CHANGED` (Apply страницы → перезапуск или `didChangeConfiguration`).
- Точка расширения 2026.1 — `com.intellij.platform.lsp.integrationProvider` (`LspIntegrationProvider.fileOpened` → `LspClientDescriptor`);
  `LspServerSupportProvider` / `LspServerDescriptor` уже `@Deprecated`. Дескриптор — один на открытую папку: `createCommandLine` из
  `RoslynLanguageServer.arguments`, `getWorkspaceConfiguration` из `RoslynLanguageServer.configuration`, `isSupportedFile` = `.cs`.
- **URI — с обычным двоеточием.** Платформа пишет `file:///c%3A/...` (как VS Code), а сервер 5.12 с таким URI считает документ посторонним
  (misc: нет ошибок компилятора, все `using` «лишние») и не находит папку для `--autoLoadProjects`. Дескриптор переопределяет `getFileUri`.
  Регистр буквы диска не важен. Проверено зондом и в живой IDE.
- **Теги диагностики.** Roslyn шлёт в `tags` числа Visual Studio, lsp4j превращает их в `null`, и с `null` в `context.diagnostics` сервер отвергает
  `textDocument/codeAction` целиком. Лечится `RoslynServerWrapper` (`LspClientManager.addLsp4jServerWrapper`, `@Internal` — риск при смене платформы).
- **Три умолчания платформы «только для TEXT и TextMate»**: semantic tokens, rename и document highlights — у C# свой язык, поэтому все три
  включены явно (`shouldAskServerForSemanticTokens`, `shouldRunRename`, `shouldAskServerForDocumentHighlights`). Других таких в API 2026.1 нет (проверено по байткоду).
- **Клиентские команды `roslyn.client.*`** (`peekReferences`, `nestedCodeAction`, `fixAllCodeAction`) исполняет клиент: `RoslynClientCommands`.
  У платформы два поколения API сразу — переопределять обе перегрузки `executeCommand` (completion зовёт устаревшую) и `codeLensClicked` (клик по
  code lens идёт мимо `commandsCustomizer`). Применение правки: `LspIntentionAction.isAvailable()` обязателен перед `invoke()` — без него `invoke` молча ничего не делает.
- **Автопопап после пробела**: пробел — trigger-символ Roslyn, сервер отвечает на нём `null`, платформа запоминает «пусто» (`EmptyAutoPopup`), и следующее
  слово остаётся без popup. `RoslynCompletionRestart` перезапускает такой completion первой буквой.
- **Фаза 7.** Go to Implementation: платформа ищет исходный элемент через `TargetElementUtil` (нужна PSI-ссылка) и реализации через PSI —
  для C# плагина не работает ни то, ни другое, а LSP-клиент платформы `implementation` не шлёт. Действие `GotoImplementation` подменено
  (`overrides="true"`, тексты — из `ActionsBundle` платформы, иначе пустой пункт меню) и для C# с загруженным сервером спрашивает сервер.
  Декомпилят (`MetadataAsSource`) — только для чтения (`WritingAccessProvider`), заголовок вкладки и баннер из `#region Assembly …` в начале файла.
  Переименование файла с типом — `RoslynFileRename` по ответу `textDocument/rename` в обёртке сервера; ждёт, пока платформа применит правку.
- **Ctrl+наведение**: платформа резолвит LSP-ссылки только во время Go to Declaration; для наведения — свой `implicitReferenceProvider`.
- **Сначала трафик, потом код.** Формы ответов Roslyn не угадывать: `tools/roslyn-lsp/capture.py` снимает запрос каждого типа, фикстуры и тест
  на потери в lsp4j — в `src/test/resources/roslyn/capture-5.12`. Новую версию сервера сначала прогонять через захват.
- Folding платформа регистрирует на любой язык (`language=""`), onTypeFormatting по умолчанию выключен (включён в дескрипторе).
- Запрос `textDocument/diagnostic` без `identifier` (так шлёт платформа) отдаёт всё сразу — компилятор и анализаторы; обход не нужен.
- Нестандартное: `getLsp4jServerClass` — свой интерфейс с `solution/open`, `project/open`; свой `Lsp4jClient` с
  `workspace/projectInitializationComplete`, `workspace/_roslyn_projectNeedsRestore` (пока только в лог). После `serverInitialized` →
  `solution/open` из `SolutionService`; нет solution — `project/open`. С `--autoLoadProjects` (умолчание страницы) клиент ничего не называет:
  сервер сам находит solution и тоже шлёт `projectInitializationComplete` (проверено), а второе открытие загрузило бы всё дважды.
- Состояние «грузится»: до `projectInitializationComplete` без ложных ошибок, работают эвристики; виджет статуса (loading / ready / crashed), Restart.
- Установка: `dotnet tool install --global roslyn-language-server` действием из нотификации; проверка runtime .NET 10.
- Хозяин там, где есть и своё, и серверное (folding, отступы при наборе / onTypeFormatting, форматирование), — сервер, см. «Решения»; в фазе 2 это
  надо провести по коду: свои реализации отключаются, когда сервер этого проекта готов.
- Semantic tokens → палитра Rider, уже сделанная в плагине (`LspSemanticTokensSupport.getTextAttributesKey`).
- Дописать самим, чего в платформе нет: Go to Implementation (`LspClient.sendRequest`), metadata-as-source (декомпилированные исходники),
  вложенные code actions и Fix All, переименование файла вместе с типом. Ошибок по закрытым файлам (`workspace/diagnostic`) платформа не умеет —
  остаётся диагностика сборки.

## Слой 2. Кэш ответов сервера — сделано (фаза 3, 2026-09-21)
Точка для всего слоя — обёртка сервера `RoslynServerWrapper` (`LspClientManager.addLsp4jServerWrapper`, `@Internal`): кэши платформы
(`LspSemanticTokensCache` и др.) внутренние, а все запросы и платформы, и плагина проходят через обёртку. Она же ведёт учёт времени каждого запроса
(`RoslynRequestStats`, меню .NET → Language Server Timings: первый вызов, медиана, максимум, ответы из кэша, запросы прогрева отдельно).

1. **Прогрев — сделано** (`RoslynWarmUp`). После `projectInitializationComplete` в активном файле, в первом `имя.член` тела: completion после точки и
   по имени, hover, definition, document highlight, code actions, workspace symbols — по одному, последовательно. Замер в живой IDE: первый completion
   пользователя **42 мс** вместо 153 холодных, code actions 86–149 вместо 523, hover 7,5. **References не прогреваются**: их цена — поиск
   конкретного символа, а не «первый раз» (517 мс у пользователя после прогрева в 585 мс).
2. **Персистентный кэш — только semantic tokens** (`RoslynTokensCache`, `<system>/dotnet-support/lsp-cache/semantic-tokens`, 64 МБ, LRU). Ключ —
   SHA-256 от легенды сервера и текста файла: захват показал, что одинаковый текст даёт одинаковые tokens. Пока solution грузится, обёртка отвечает
   из кэша (платформа спрашивает, только если кэш для этого текста есть — `hasCachedTokens`), эвристическая раскраска для такого файла уступает;
   после загрузки `refreshSemanticTokens` — и платформа берёт настоящий ответ. В кэш пишутся только ответы загруженного сервера, и только если текст
   не изменился за время запроса. Вживую: при старте IDE первый ответ tokens — из кэша за 0 мс, через 1,15 с после старта процесса, на 2,8 с раньше
   загрузки solution. Folding, symbols и inlay hints **не кэшируются**: до загрузки их дают эвристики плагина (folding, Structure view), inlay hints
   выключены по умолчанию.
3. **Спекулятивный completion — не делается, по замерам.** Сервер на пробеле отвечает `null` (заготовить нечего); при открытом списке платформа
   не перезапрашивает — после первой буквы `isIncomplete: false` и список не меняется до конца слова (630 элементов на `C`…`Console`, 50 после точки).
   Ждёт пользователь только первую букву слова и точку: 10–20 мс у прогретого сервера, около кадра. Спекуляция сэкономила бы эти 10–20 мс ценой
   рисков из «Рисков» №1 (у платформы нет точки подложить свой список и дослать настоящий). Вернуться, если замер в IDE на большом solution покажет
   больше 50 мс на первую букву.
4. **Инвалидация.** Ключ tokens — содержимое, правка файла сама даёт промах; другой сервер — другая легенда; после загрузки кэш не используется
   вовсе, так что правки `.csproj` / assets ему не опасны. Статистика и память о раскрашенных из кэша файлах сбрасываются при старте сервера.

Факты, на которых стоит слой (`tools/roslyn-lsp/capture.py`, записи `cache …`): completion после пробела — `null`; tokens детерминированы; файл в
4 154 строки — 170–500 мс на tokens и 375 КБ JSON на **каждый** запрос (платформа просит только `full`, без delta и range: `client-capabilities.json`);
первый completion по имени, если он — самая первая работа сервера, приходит урезанным (154 из 630, без `Console`) с `isIncomplete: false`, а после
pull-диагностики — целым (в IDE диагностика всегда первая).

Не кэшируются никогда: диагностика и правки кода (rename, code actions) — устаревший ответ там хуже медленного.

## Слой 3. Свои данные плагина
Отвечают на всё, что спрашивается **по имени**: какие типы есть, в каком namespace, какие члены у типа `Console`, документация члена.
Не отвечают на «какой тип у выражения `person.Friend`» — вывод типов, перегрузки, generics остаются за Roslyn.

### Исходники — расширить `CSharpDeclarationIndex`
Уже есть (`lang/CSharpNavigation.kt`): `ScalarIndexExtension<String>` на платформенном `FileBasedIndex` — инкрементальный, переживает рестарт IDE,
хранит только имена типов и членов, питает Go to Class / Symbol.
- Сделать индекс со значением: namespace, вид, модификаторы (`static`, `partial`, доступ), базовые типы, сигнатуры членов, признак
  extension-метода и расширяемый тип. Отдельно по файлу: `using`-и, `global using`, `using static`, псевдонимы.
- Источник — `CSharpDeclarations.scan`; чего сканер не видит (типы параметров, базовые типы) — добавить чистыми функциями с тестами.
  Каждое изменение состава — поднять `VERSION`.

### Метаданные сборок — главный выигрыш
Типы и члены NuGet-пакетов и ref-pack'ов фреймворка **неизменны** для пары «пакет + версия + TFM»: считается один раз на машину, переиспользуется
всеми проектами и сессиями (у пользователя 674 пакета в `~/.nuget/packages`, ref-pack'и 9.0 и 10.0).
- Список сборок проекта уже есть: `project.assets.json` (`SolutionService`) → compile-time assets по TFM; фреймворк —
  `<dotnet>/packs/Microsoft.NETCore.App.Ref/<версия>/ref/<tfm>` (+ AspNetCore, WindowsDesktop).
- Чтение dll — маленький **dotnet-помощник** на `System.Reflection.Metadata` (без загрузки сборок): на вход пути dll, на выход JSON Lines —
  публичные и protected типы, члены с сигнатурами, `static`, extension, `[Obsolete]`. Тот же помощник, что запланирован под dotPeek / ClrMD.
  Разбор ECMA-335 на Kotlin — лишняя работа.
- Хранение — уровень приложения: `<system>/dotnet-support/metadata/<id>/<version>/<tfm>.bin` + версия формата; для dll вне пакета ключ — путь +
  размер + mtime. В память — лениво, по проекту. Расчёт — фоном после открытия solution и после restore; посчитанное не трогается.
- Нет `dotnet` / помощника — этих данных просто нет, остальное работает.

### XML-документация
`*.xml` рядом с dll, doc-id → `summary` / `param` / `returns`; хранится тем же ключом, что метаданные. Hover и документация в completion для
фреймворка и пакетов без сервера.

### Что это даёт
- Go to Class / Symbol по solution **и по пакетам** сразу после открытия проекта.
- Completion имён типов, включая неимпортированные, с авто-`using` (у Roslyn это дорогая опция, её часто выключают).
- `Console.`, `Math.`, любой статический или полностью названный тип, `enum` — члены < 1 мс; extension-методы по имени расширяемого типа.
- Раскраска имён типов по данным вместо эвристики, пока нет semantic tokens; документация по наведению, пока сервер не ответил.

Чего свои данные не видят: `#if`, global usings из SDK (`ImplicitUsings`), source generators, `InternalsVisibleTo`, псевдонимы сборок;
partial-типы склеивать по полному имени. Лечится не точностью, а правилом «только предлагают».

## Риски
1. **У платформенного completion нет точки для своего источника списка** (`LspCompletionSupport` — только фильтр и рендер). Тогда
   `LspCompletionDisabled` + свой `CompletionContributor` через `LspClient.sendRequest`; синхронизация документов остаётся платформенной.
2. **Платформа шлёт только `semanticTokens/full`** (range и delta не использует) — на больших файлах дорого; лечится персистентным кэшем, при
   необходимости — своим запросом range.
3. **Нестандартные расширения Roslyn** плохо документированы и меняются между версиями: фиксировать поддерживаемые версии сервера, снятый трафик
   хранить фикстурами, `bench.py` / `probe.py` прогонять на новой версии.
4. **Ресурсы**: отдельный процесс на сотни мегабайт; все функции должны жить в состоянии «ещё грузится».
5. **Размер метаданных**: ref-pack — тысячи типов, сотни тысяч членов. Компактный бинарный формат, ленивая загрузка по namespace; мерить в фазе 5
   до того, как строить потребителей.
6. **Помощник — ещё один артефакт**: класть dll в ресурсы плагина, запускать `dotnet <helper>.dll`, версионировать формат вывода.
7. **Дубли в lookup** при слиянии своих данных с ответом сервера: нужен устойчивый ключ элемента (вид + полное имя + сигнатура).
8. **Узкое место — проверка, а не код**: редакторный UX headless-тестами не покрыть.

## Как проверять
- Чистые функции (аргументы, конфигурация, ключи кэша, разбор вывода помощника и XML) — юнит-тесты без процесса.
- Клиент и кэш — платформенные тесты (`myFixture`) с фейковым сервером на записанном трафике; реальный сервер и `dotnet` в тестах не запускать.
- Скорость — `tools/roslyn-lsp/bench.py` для сервера и замеры в живой IDE до и после каждого кэша.
- UX — UI-робот (`tools/ui-robot`) на копии `debug-playground`, остальное — пользователь вживую.
